# Выполнение следующего этапа CITA Route

База: опубликованная 0.6.4. Ветка: codex/adaptive-platform-next.
Этот файл — журнал реализации, а не подтверждение готовности функций.

| Этап | Состояние и критерий приёмки |
|---|---|
| 1. Координация | Уже есть operation/setup/update gates и поколения. Проверить новую операцию обслуживания зависимости против Start, Stop, setup, обновления и диагностики; общий охват нескольких копий клиента остаётся обязательным. |
| 2. Зависимости | В работе: различать отсутствие, legacy 2.x, неполную установку, поддерживаемую и непроверенную новую версию; проверенная stable не равна newest/beta. Проверить официальную загрузку и миграцию на ВМ. |
| 3. Наблюдения | Есть раздельные DNS/TLS/body и измерения. Нужен аудит классификации и причин для UI без ложного заявления о блокировке. |
| 4. DNS/IPv6 | Есть ограниченный IPv4/DNS fallback. Полный IPv6, DoH и несколько адресов требуют отдельной реализации/приёмки; неизвестный домен не получать из общего IP. |
| 5. Память | Есть network epoch, TTL, warm hints. Проверить смену сети/профиля, ручной приоритет, сохранение TTL и ограничение фоновой нагрузки. |
| 6. Первое обращение | FirstUseGate остаётся experimental/off. Подтвердить дедупликацию, отмену, лимиты и отсутствие повторного выполнения запросов пользователя. |
| 7. Зависимости сайта | Браузерный адаптер уже есть, opt-in. Связь повышает приоритет проверки, но не наследует путь. Проверить общий CDN и независимые приложения. |
| 8. Устойчивость | Есть адресный ремонт и отмена старых health checks. Полный VPN-only transport boundary и политика отказа требуют отдельной приёмки; не обещать перенос живого TCP между IP. |
| 9. Ресурсы | 0.6.4 исправляет Windows read/close leak. Замерить финальные новые компоненты и цену фона/свёрнутого GUI. |
| 10. Интерфейс | Compact/Advanced и стадии уже есть. Добавить понятную совместимость WireSock, обслуживание и объяснение решений без секретов. |
| 11. Обновления | Framework-only CITA update есть. Новые зависимости только с закреплённой версией/хешем/подписью и безопасным обслуживанием. Автооткат драйвера не считать доказанным. |
| 12. Матрица | Короткие тесты до 10 минут, отказные сценарии и реальная ВМ. Не включать долгий soak; не заменять тест Win10 тестом Win11. |

Ограничения: рабочий VPN/hosts основного ПК не менять. Тестовый peer не
использовать одновременно в двух ВМ. Не публиковать новый релиз до сборки и
приёмки. Профили, ключи, токены и история посещений не входят в поставку.

## Реализовано в этой ветке

- Оценка версии/редакции и доверия к CLI. Новая непроверенная версия не понижается.
- Закреплённая официальная 3.6.1.1 x64, 17 659 128 байт, SHA-256
  `734F3090BA095A698F7293FF90EBD6DC64FCD646277011DFA3648AC5DBDF5D37`.
  Проверяется Authenticode издателя The Anti-Cloud Corporation и точный хеш;
  переадресация, другой размер и подменённый файл отклоняются.
- Кнопка установки/обновления в настройках, уведомление при запуске, opt-in
  автообновление совместимой старой 3.x при отключённом маршруте. Beta и 2.x
  автоматически не устанавливаются. Каталог меняется с проверенным выпуском CITA,
  удалённого подписанного каталога пока нет.
- Проверка загрузки до остановки своего маршрута, координация со службой,
  запрет обновления при чужом активном профиле. Журнал неполной установки
  блокирует новое подключение до проверки; состояние включено в обезличенную диагностику.
- Общий mutex операций разных копий CITA; право передаётся дочерней транзакции
  подключения/настройки и установщику CITA. Stop остаётся доступен владельцу
  обновления. Это не блокирует ручные действия в сторонних программах.
- Просмотр причин и давности решений в Advanced, без полного пути приложения.
  Будущие даты, другая сессия и неподтверждённая публикация не становятся успехом.
- Явная диагностика домена: bounded IPv4/TCP HTTPS direct/DPI/VPN, общая direct/DPI
  DNS-проба, две проверки содержимого, ограничение одного запуска на машину.
  Не меняет маршруты, не передаёт URL пути/параметры, не выполняет запросы пользователя.
- HTTP-отказы/редиректы не считаются прочитанным содержимым. До двух редиректов
  внутри того же HTTPS-домена допускаются в прежнем 3-секундном бюджете, без cookies.
  Cross-host, HTTP, credentials и нестандартные порты запрещены. Стратегия кэша v5
  исключает применение решений старой семантики.
- UI сохраняет привязку неизменившихся строк; подсчёт доменов большого списка
  повторяется при изменении файла, а не каждый тик. Ошибка чтения повторяется через 5 с.

## Открытые пункты — не считать завершёнными

- Миграция реальной 2.4, поведение старого split-tunnel, полный жизненный цикл
  vendor installer и перезагрузка. Переход 3.4.8.1 → 3.6.1.1 уже проверен
  на Win10 с синтетическим профилем: trusted CLI, команды управления и семантика
  экспортированных параметров сохранены. Это не проверка произвольных профилей.
- Проверка нагрузки всего работающего клиента и оставшихся отказных сценариев.
  Синтетический замер UI после оптимизации и GUI self-test уже пройдены.
- Реальная IPv6-сеть, разные DNS/DoH и новая матрица приложений/сетей.
  Win10 Enterprise 2016 LTSB: framework installer сам загрузил .NET 10.0.13,
  установка и self-test завершились с кодом 0 после исправления сети самой ВМ.
- Системный принудительный VPN-only boundary, позволяющий безопасно удерживать
  VPN-сокеты при исчезновении перехвата; настоящий перенос TCP между выходами.
- Подписанный удалённый каталог компонентов/правил, управление ключами подписи
  и подтверждённый откат драйвера. SHA-256 вместе с HTTPS не заменяет такой каталог.
- Сборка окончательного пакета, CI/публикация. Версия продукта пока не изменена.

Короткая приёмка не заменяет долгую стабильность. Длительные тесты по просьбе
пользователя не запускаются.

## Уточнение объёма и рабочего процесса

Решение пользователя: не расширять матрицу миграции старых WireSock. Критерий —
актуальная проверенная stable, доверенный CLI и поддержка нужных команд.
Неподходящая установка требует обновления; beta не считается stable.

Экономия контекста: структурный поиск через CodeGraph, чтение только нужных
фрагментов, связанные проверки одним прогоном, повтор только после изменений
или нового отказа. Долгие команды опрашивать с интервалом 20–30 с, а не
каждые 5 с; сохранять компактные результаты, не перечитывать целые журналы.
Не добавлять агентов, длинные тесты и новые сценарии без необходимости.

## VPN-only boundary: проверка совместимости

Обычный outbound block Windows Firewall по пути vpn-bridge.exe в W11 отклонён:
HTTPS до правила Verified, при правиле ControlHttpsUnavailable, после удаления
Verified. Правило удалено, клиент остановлен, прежняя привязка службы возвращена.
Receipt runtime/vm-lab/w11/boundary-feasibility.json; это отрицательный результат
проверки идеи, не готовый killswitch. В производственный путь правило не добавлено.

Причина архитектурного ограничения: transparent WireSock перехватывает пакеты
через NDIS; приложение создаёт обычные сокеты на физическом интерфейсе. WFP block
по приложению перекрывает и трафик, который затем должен был попасть в туннель.
Штатный Network Lock WireSock блокирует весь интернет, что конфликтует с прямой
частью CITA. Следующая проверка — отдельный virtual adapter WireSock, bind bridge
к нему и block physical interfaces только для bridge. Системные маршруты и
совместимость split tunnel обязательно проверяются отдельно; без теста не включать.
Источники: https://www.wiresock.net/documentation/wiresock-secure-connect/virtual-adapter-mode.html
https://wiresock.net/documentation/wiresock-secure-connect/network-settings.html
https://www.ntkernel.com/wiresock-secure-connect/

Виртуальный режим: интерфейс создан, HTTPS VPN подтверждён, но независимый direct
не совпал с исходным физическим выходом. Повтор с direct через то же ядро и
bind_interface физической NIC дал тот же отказ критерия разделения. В продукт
не интегрирован. Это ограничение проверенной схемы, не доказательство невозможности
любого split tunneling в WireSock. Нужна отдельная архитектура изоляции/маршрутов,
а не отключение текущей safety pause ради сохранения TCP.

Скрипт стенда исправлен: исключены alias Cli/Clear-Item, BOM в JSON ядра,
прямой source-IP bind отличён от bind_interface ядра, принят документированный
ненулевой disconnect при независимо подтверждённом Disconnected. Предыдущие
неполные cleanup вручную доведены до восстановления managed profile и owner.
Receipt: runtime/vm-lab/w11/virtual-boundary.json, virtual-boundary-cleanup.json.

Вариант с временными physical /1 routes частично подтвердил идею:
virtual-boundary первый прогон показал directPreserved=true,
vpnWithPhysicalBlock=true, disconnectedProxyBlocked=true, bridgeRetained=true,
но directAfterDisconnect=false. Следующий такой же прогон не подтвердил даже
стабильность разделения до разрыва (directPreserved=false). Поэтому приёмка
НЕ пройдена; сохранение VPN TCP не тестировалось и не заявляется.
Последний прогон: managedProfileRestored=true, originalOwnerRestored=true,
ruleRemoved=true, temporaryRoutesRemoved=true. Основной ПК не менялся.
Receipt: runtime/vm-lab/w11/virtual-boundary-routes.json.

Дальнейший критерий для производственного boundary:
1. Явная отдельная таблица/compartment или другой транспорт вместо общего
   default route виртуального адаптера; сохранённый физический direct/DNS.
2. Запрет исходящего plaintext на всех физических NIC для VPN-компонента,
   включая новые NIC и IPv6, независимо от GUI/Watch/службы WireSock.
3. Подтверждённый разрешённый шифрованный путь; socket/packet-level fault injection,
   проверка TCP и UDP по отдельности, capture на физическом интерфейсе.
4. Владение/жизненный цикл фильтров: Stop, crash, update, uninstall, rollback;
   нельзя включать удержание моста на основании одного здорового HTTPS.
5. Пока все критерии не пройдены, production сохраняет нынешнюю safety pause.

Не превращать WinpkFilter static filters в общую таблицу наугад: это рискует
конфликтовать с фильтрами WireSock. Обычный ALE app-block несовместим с текущим
NDIS transparent путём; общий WireSock network-lock нарушает direct traffic.
