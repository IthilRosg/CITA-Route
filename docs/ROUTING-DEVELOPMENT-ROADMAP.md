4. **Продолжить ускорение отдельным экспериментом.** Успешное установление TCP

## Результат пересмотра

Улучшать нужно четыре разные вещи: определение рабочего пути, применение решения,
восстановление компонента и сохранение уже открытого соединения. Одна успешная
HTTPS-проба не подтверждает их все. Цель «99%» имеет смысл только на объявленной
матрице приложений, сетей и отказов; универсальная доступность всех сервисов
не гарантируется даже при исправном клиенте.

Важные изменения относительно предыдущего порядка:

- DNS и перебор адресов идут до ускорения первого соединения: в базе 0.6.0
  проверялся только первый IPv4 из ответа одного DoH-резолвера на каждом пути.
  Ограниченное исправление в рабочей ветке описано в отдельном отчёте выше.
- Исследование принудительной границы VPN начинается сразу. Пакетный DPI и новые
  варианты перехвата не выпускаются до проверки реального сочетания драйверов.
- Резерв поверх TCP/TLS важнее расширенного пакетного DPI при полном отказе UDP.
  Можно разрабатывать их параллельно, но нельзя считать взаимозаменяемыми.
- До собственного relay проверяется сохранение существующего WG/AWG-туннеля при
  смене физической сети и отказ от лишних перезапусков.
- Пользовательский SOCKS-модуль DPI рассматривается раньше дополнительного
  пакетного драйвера; пригодность каждого метода на Windows проверяется отдельно.
- Подписанные обновления и профили стратегий — сквозная работа, которая должна
  завершиться до автоматической доставки новых исполняемых модулей/стратегий.

## Обязательные контракты

### Уточнения второго пересмотра, 2026-10-21

Повторная проверка выявила дополнительные условия, которые должны войти в
этапы 1–3 до расширения числа транспортов. Это выводы по коду и архитектуре;
численный выигрыш и воспроизводимость на реальном драйвере ещё не измерены.

**Ожидание кандидатов и время пользователя.** В `PolicyTransport.Select`
задачи запускаются параллельно, но ожидаются в порядке direct → DPI → VPN
(`agent/PolicyTransport.cs:166–176`). Готовый резерв может ждать двух неудачных
проб предпочтительного пути. Это сохраняет приоритет direct, но ограничивает
ускорение. Нужен ограниченный срок предпочтения direct, выбранный по измерениям,
с немедленным переходом при подтверждённом отказе. Известный рабочий путь
используется сразу; дорогое уточнение причины выполняется в фоне. Простая
гонка «первый ответивший победил» непригодна: она может необоснованно увести
большую долю трафика в VPN. История отказов действует только в своей области
и не создаёт вечного запрета direct.

`RouteSelection.Milliseconds` получает длительность выбранного кандидата,
а не всё ожидание выбора (`agent/PolicyTransport.cs:176,186`). Общая длительность
калибровки отдельно сохраняется в `PolicyWorker`. В новых метриках явно разделить
очередь, готовность кандидата, принятие решения, подтверждение применения и
первый полезный результат реального приложения. Иначе быстрый probe может
создать видимость быстрого первого подключения.

**Проба и реальное соединение должны иметь согласованную семантику.** Улучшение
перебора IP только внутри PolicyTransport недостаточно. Проверить, как реальный
движок выбирает адрес после такого решения. Если проба прошла на втором IP,
а приложение/движок снова обращается к нерабочему первому, доступ не восстановлен.
Резерв DNS также должен быть согласован с реальным DNS-путём, а не существовать
только в диагностике. Проверять фактический peer IP, исходный hostname, семейство,
DNS-путь, транспорт и применённую версию правила. Не переписывать произвольный
IP назначения приложения на основании ненадёжного предположения о домене.

В `PolicyTransport.Resolve` уже есть два резолвера, но `SelectResolved` использует
свой Lookup с одним резолвером. Исправление должно затрагивать действующий путь
калибровки и соответствующий путь данных; наличие вспомогательной функции само
по себе не доказывает резервирование. Собственный .NET HTTP/1.1 probe остаётся
отдельным профилем проверки, а не точной копией браузерного TLS/H2/H3.

**Доступность и причина — разные результаты.** Для восстановления достаточно
подтверждённого разрешённого пути; доказательство вмешательства провайдера может
потребовать гораздо больше времени. Не ставить OONI, Globalping или классификацию
«РКН/не РКН» в цепочку открытия сайта. Сохранять доступность и объяснение отдельными
полями. Неустановленная причина не запрещает использовать подтверждённый путь.

**Аутентификация кандидата не равна аутентификации всех путей.** Сейчас ошибка
сертификата предпочтительного кандидата прерывает Select до выбора остальных
(`agent/PolicyTransport.cs:159–175`). Это существующее консервативное поведение,
которое нельзя менять простым игнорированием ошибок TLS. Отдельно спроектировать
политику: отказать именно кандидату с неверным сертификатом; разрешать альтернативу
только при независимой успешной проверке исходного hostname и соблюдении всех
ограничений пользователя. Для строгого режима может сохраняться общий отказ.
Тесты: неверный сертификат только direct, на всех путях, истёкший сертификат самого
сайта и временный отказ DNS. Никаких trust-all/подмены hostname ради успеха пробы.

**Связанные соединения сервиса.** Закрепление одного потока не сохраняет внешний
IP всех запросов авторизации/API/media. Добавить ограниченную привязку выхода
для явно описанного сервиса или приложения, если его сценарий требует постоянства
IP. Состав зависимостей и срок должны быть определены; принадлежность одному CDN
не объединяет сайты. Не читать cookies/учётные данные для определения группы.
Ручные ограничения сохраняют приоритет; несовместимая группа не расширяет права.
Возврат на direct откладывается до подходящей границы/истечения привязки, а отказ
текущего выхода запускает заданную политику восстановления. Это уменьшает риск
обрыва прикладной сессии, но не гарантирует её сохранения при смене внешнего IP.

**Общий отказ не должен запускать тысячи одинаковых проб.** Нужна иерархия
состояний: физическая сеть → DNS/транспорт → назначение → поток. Переоценку общей
зависимости объединять и ограничивать, сохраняя независимые рабочие пути.
Отказ одного сайта не выключает транспорт; факт отсутствия сети не записывает
в кэш блокировку каждого домена. Возвращение зависимости сначала проверяется
ограниченной пробой, затем снимаются соответствующие ограничения. Проверка
разных доменов через один сломанный резолвер не является независимым свидетельством.

Ближайшая приёмка этих уточнений: управляемые сценарии на небольшом корпусе,
одинаковые исходные состояния и сравнение с 0.6.0. Миллион доменов не является
предварительным условием для исправления перечисленных механизмов.

### Общие требования

1. **Один координатор действий.** События, health, policy, GUI и обновление сообщают
   причины существующему владельцу перехода. Stop, смена профиля и поколение
   отменяют старые операции. Внешнее отключение не превращается автоматически в
   бесконечное восстановление. Политика переключения мешающего стороннего VPN
   применяется отдельным управляемым переходом.
2. **Разрешение пути предшествует его оценке.** Сначала проверяются локальное
   назначение, служебные соединения и специальные пространства адресов; затем
   применяются ограничения пользователя. Противоречие «локальный tailnet-адрес» и
   «этот адрес только через публичный VPN» получает явную ошибку/диагностику, а не
   скрытое ослабление запрета. Автоподбор выбирает только из разрешённых вариантов.
3. **Решение имеет область.** Сеть/эпоха, экземпляр приложения, назначение с
   происхождением имени, порт, протокол, IP-семейство, стратегия, транспорт и
   версия правил. PID без времени создания недостаточен; общий CDN-IP не является
   достоверной идентичностью сайта. Смена профиля меняет доверие к выходу.
4. **Факт отделён от намерения.** Записываются запрошенный и фактический выход,
   применённая версия правил, этап отказа и достаточность доказательств. Unknown
   не считается подтверждением доступности direct. Разрешённый direct по
   умолчанию остаётся решением политики, а не доказанным успехом; запрет прямого
   выхода относится только к правилам, где он задан. Отсутствие события также
   не подтверждает исправность наблюдателя.
5. **Поток закрепляется за путём.** Существующий TCP нельзя переносить на другой
   внешний адрес обычным изменением правила. Прикладные байты и неизвестные
   зашифрованные операции не дублируются; TLS 0-RTT не используется в гонке путей.
6. **Проверки ограничены.** Общие бюджеты времени, памяти, портов, очередей и проб;
   объединение одинаковых запросов; справедливость между приложениями; backoff
   с jitter. При перегрузке сокращается телеметрия, пользователь получает
   определённый результат в срок, запреты маршрутизации не снимаются.
7. **Состояние имеет срок и поколение.** Время ожидания считается монотонными
   часами; перезапуск/сон/изменение системного времени не оживляют старую пробу.
   Сетевые события объединяются; изменения собственных интерфейсов не создают
   цикл восстановления. Переоценка кэша не требует закрытия всех потоков.

## Этапы и условия завершения

| Этап | Что делаем | Когда можно переходить дальше |
|---|---|---|
| 0. База 0.6.0 | Длительный прогон второго ПК, Tailscale SSH/MagicDNS, реальный updater; фиксированная матрица и воспроизводимые отказы | Есть раздельные результаты по сценариям и свежая диагностика отказов; найденные регрессии разобраны |
| 1. Наблюдение и модель решения | Структурированные события движка, причины/версии/поколения, ограниченный IPC, оценка в режиме наблюдения без изменения маршрутов | События совпадают с реальными потоками; потеря/задержка событий обнаруживается; старое поколение ничего не применяет |
| 2. DNS и выбор адреса | Несколько адресов, отказоустойчивое разрешение, семейства IP, достоверность имени, специальные DNS-маршруты | Отказ одного адреса/резолвера не объявляет весь сервис заблокированным; tailnet и выбранный выход не ломаются |
| 3. Быстрый выбор и мягкое восстановление | Решение в памяти до пользовательских байтов, ограниченный бюджет, подтверждённый резерв; сохранение исправных компонентов | Нет повторных операций и массового обрыва исправных потоков; выигрыш времени подтверждён против 0.6.0 |
| 4. Независимый транспорт | Один проверенный TCP/TLS-вариант, отдельная серверная настройка и проверка выхода; затем второй адрес/провайдер | При блокировке UDP доступен разрешённый резерв; отказ одного IP не маскируется другим портом того же IP |
| 5. Управляемый DPI | Сначала SOCKS-прототип; пакетный WinDivert-вариант только после отдельной приёмки границы и драйверов | Есть измеримый выигрыш на выбранной матрице без циклов перехвата, утечек и роста ресурсов за пределами бюджета |
| 6. Качество UDP/QUIC/MTU | Сценарные измерения, отдельные оценки качества и корректный выбор транспорта для голосовых/игровых потоков | Результат подтверждён приложением и контролируемыми сетевыми отказами, а не одним STUN/HEAD |
| 7. Сохранение сессий через anchor | Только при подтверждённой необходимости: изолированный прототип relay с сохранением состояния | Сохраняются заданные TCP/UDP-сценарии; проверены потери, паузы, память, повторный вход и отказ самого anchor |

Исследование VPN-границы и защита доставки идут параллельно этапам 0–2.
Этапы 1–2 можно начинать до получения длительных логов; их результат не меняет
сборку продолжающегося прогона. Этапы 4 и SOCKS-часть 5 могут разрабатываться
параллельно после общих контрактов. Пакетный DPI и изменение архитектуры перехвата
имеют обязательный барьер реальной WFP/WireSock-проверки. Для экспериментального
выхода в пилот нужна явно описанная граница возможностей; функция принудительного
VPN-only не объявляется обеспеченной там, где она не доказана.

## Уточнение реализации этапов

### 0–1. Измерения и события

Задать эталонные сценарии с независимым ожидаемым результатом. Классификатор не
может сам служить эталоном своей точности. Различать ошибку одного назначения,
выхода и всей физической сети. Отдельный таймер проверяет прогресс наблюдателя.
До изменения поведения зафиксировать в протоколе матрицы численные бюджеты
холодного/тёплого выбора, восстановления и ресурсов; менять их только с
обоснованием и сравнением с базой, а не подгонять после неудачного теста.
В IPC нужны ACL, идентификация отправителя, предел размера/частоты, версионирование
и работа при отсутствии GUI. Для SYSTEM/нескольких пользователей нельзя доверять
произвольному файлу или сообщению обычного процесса как команде изменения сети.

Локально хранить минимум метаданных: не полные URL, тела, cookies, токены и ключи.
Диагностика по умолчанию не отправляется в публичную базу измерений. Домены тоже
могут раскрывать историю использования; экспорт должен иметь понятную очистку.

### 2. DNS, идентичность и несколько адресов

Ограниченный перебор нескольких A/AAAA в духе Happy Eyeballs, с отдельной историей
семейств и бюджетом всей операции. Кэш учитывает TTL, отрицательные ответы и
эпоху; временный отказ не записывается как постоянная блокировка домена. Несколько
резолверов не означают гонку каждого запроса ко всем: нужен ограниченный резерв.
Bootstrap DoH и собственные служебные сокеты не должны уходить обратно в TUN.

Проверять DNS для выбранного выхода, чтобы direct-ответ CDN не навязывался VPN.
Сохранять HTTPS/SVCB и ECH-совместимость, не выключать DoH/ECH глобально ради SNI.
При собственном DoH приложения имя может остаться неизвестным. При H2/H3 одно
зашифрованное соединение может обслуживать несколько origins: классификация по
первому имени не даёт посайтового управления всеми последующими запросами.
При отсутствии достоверного имени применять заранее определённую политику
приложения/назначения и показывать ограничение в расширенной диагностике.

LAN, Tailscale IPv4/IPv6, MagicDNS/Quad100, subnet routes и exit node проверять
раздельно. Существующие исключения нельзя заменять общей отправкой DNS напрямую.
Учитывать фактический интерфейс/NRPT и переименование адаптера. Для проб
публичных сайтов исключать непреднамеренные обращения к локальным/служебным
адресам после DNS-ответа или редиректа.

### 3. Ускорение и восстановление

Кэшированное разрешённое решение применяется без ожидания фоновой калибровки.
На холодном назначении используются короткая проверка и заранее подтверждённый
разрешённый резерв. Его отсутствие заканчивается понятным отказом в бюджете;
VPN-only не подменяется direct. В обычном режиме direct-first разрешённый прямой
путь можно опробовать в установленном бюджете; это не делает назначение VPN-only
и не создаёт права повторить уже отправленную операцию. Числа таймаутов выбираются по холодным/тёплым
p95/p99; два полных TLS-обмена не обязаны укладываться в 1–2 с на любой сети.

Сначала прототип на одном TCP-сценарии под флагом. Независимые TCP/TLS-пробы
не содержат пользовательских данных. После отправки пользовательских байтов
прозрачного переигрывания операции нет. Если меняется только правило, старые
исправные потоки остаются на старом выходе. Подтверждение применения правила
включает версию снимка; обновление снимка не держит глобальную блокировку сети.

Порядок ремонта: перепроверить причину → исключить отказ только назначения →
переоценить новый поток → восстановить конкретный компонент → полный restart
лишь при необходимости. Единичная неудачная проба и idle-handshake не повод для
перезапуска. Параллельные восстановители не выполняют одно действие дважды.

WireGuard допускает roaming endpoint; сначала проверить, может ли наш WireSock/AWG
сохранить туннель, внутренний адрес и серверное состояние при смене внешней сети.
Это гипотеза применения протокола, а не подтверждённая возможность нашей сборки.
PersistentKeepalive включается по необходимости NAT-сценария, не принудительно
для всех профилей. Прямой TCP со старым локальным адресом при смене сети отдельно
может оборваться, даже если VPN-потоки сохранились.

### 4–5. Транспорты и DPI

Оценить TCP/TLS-протокол, уже доступный в нашем движке, например Trojan. Выбор —
после проверки фактической сборки, сервера, аутентификации, TCP/UDP-возможностей
и стоимости. Простой SOCKS-over-TLS без UDP-ассоциации не исправляет UDP-игру.
TCP-туннель с UDP-переносом может дать доступность ценой задержки при потерях.
QUIC/Hysteria не являются резервом от полного запрета UDP. Другой порт того же
IP не заменяет другой адрес/провайдера. Проверка контрольного URL не заменяет
доступность конкретного назначения.

Единый адаптер транспорта сообщает возможности, Ready/Unknown/Failed, поколение,
границу доверия и проверенный выход. Несколько одновременных профилей WireSock
не предполагаются без проверки SDK. Нативные события SDK исследуются отдельно;
существующее чтение RTT/потерь не заменять сразу новым жизненным циклом клиента.
Статистика отсутствует — значит неизвестна, а не «туннель умер».

Для DPI сравнить текущую TLS-фрагментацию с ограниченным SOCKS-прототипом ByeDPI.
Он слушает только loopback, его внешний сокет исключён из повторного перехвата,
стратегии закреплены и выбираются одним владельцем. Прежде чем использовать
внутренний авто-режим стороннего модуля, проверить отсутствие повторной отправки
реальных запросов. Поддержку методов под Windows подтверждать по каждому методу.

Если нужен zapret2/winws2, перехватывать только разрешённые direct-потоки и начало
сессии. В WinDivert NETWORK нет прямого processId: нужна корректная связь с
FLOW/SOCKET-метаданными, учёт PID/портов и гонок. Внешний пакет прокси принадлежит
прокси, а не исходному приложению — это тоже часть модели корреляции. Проверить
порядок WireSock/TUN/WFP/WinDivert, повторную инъекцию, остановку и удаление
фильтров. Одним потоком одновременно не управляют два разных DPI-модуля.

Не запускать эволюционный подбор произвольных стратегий на пользовательском
трафике. Идеи Geneva пригодны для изолированной лаборатории; сам инструмент
ориентирован на Linux/netfilter. Стартовый продуктовый механизм — небольшой
версионированный набор проверенных пресетов с наблюдением и откатом.

### Сквозная работа: VPN-граница и доставка

Сохранить отдельный протокол [TRANSPORT-BOUNDARY.md](TRANSPORT-BOUNDARY.md):
реальные WireSock и физический захват, IPv4/IPv6, смерть/зависание процесса,
смена интерфейса, перезагрузка, BFE, сон, обновление и удаление. Подтверждать
отсутствие запрещённых пакетов на физическом выходе, а не только отказ curl.
Блокировка только нашего моста не должна отключать чужие direct/LAN/Tailscale.
Нельзя просто включить виртуальный режим WireSock: он меняет системные маршруты
и DNS и требует отдельного проекта миграции. Если app-scoped решение несовместимо
с реальным перехватом, выбрать и проверить другую границу до обещания VPN-only.

Для доставки разделить целостность и независимую подлинность. Хеш из того же
GitHub Release полезен, но не заменяет подпись доверенным ключом. Рассмотреть
зрелую реализацию TUF: ротация ключей, защита от отката и устаревших метаданных,
совместимость версий агента/движка/стратегий. Не разрабатывать свою криптографию.
Недоступность обновлений или истечение метаданных не отключают работающий маршрут.
Контролируемый откат разрешается отдельной политикой, не обходом проверки версии.

Проверить реальную цепочку GUI → защищённый мост → GitHub/зеркало → установщик:
готовность нового пакета подтверждается до остановки рабочего маршрута. Установка
выполняется одним владельцем транзакции с откатом. Проверить отказ runtime,
скачивания, подписи, места на диске и внезапный restart между фазами. До поставки
нового модуля — лицензия, закреплённая версия, происхождение бинарника/драйвера,
совместимость с Secure Boot/HVCI/антивирусом без отключения защит Windows.

### 6–7. UDP и сохранение сессий

Для UDP различать бездействие, потери и невозможность обмена; фиксировать размер
и тип контрольного пакета. Показатель STUN относится к своей цепочке. MTU black
hole проверяется передачами разных размеров с обратной связью; маленький HEAD
и произвольный ICMP-ping недостаточны. Изменение MTU/MSS ограничено своим путём.
Не обещать низкий игровой ping при перегрузке общего канала: нужны отдельные
проверки очередей и ограничений фоновой передачи.

Relay нужен, если измерения покажут разрывы, не устраняемые сохранением WG/AWG
и ремонтом компонента. Сначала сравнить пакетный туннель с постоянным внутренним
адресом и потоковый relay; выбрать один узкий прототип. Он удерживает состояние
на одном сервере с начала потока. Смена публичного выхода и отказ самого anchor
не решаются автоматически. Проверить лимиты буферов, подтверждения/дубли, сроки
UDP, повторное подключение и backpressure. TLS сайта остаётся сквозным.

MASQUE/CONNECT-IP, QUIC migration и MPTCP — основы для исследования, а не готовая
гарантия сохранения любой игры. Для Windows 10 нельзя делать базовую функцию
зависимой только от System.Net.Quic; наш Go-движок уже даёт другой путь исследования.
Интеграция с CITA-AWG использует отдельное описание транспортов и полномочий;
WG/AWG-конфиг сам по себе не содержит настройки TLS/QUIC или relay.

## Приёмка и измеримость

Измерять раздельно первое подключение, успех с резервом в бюджете, ошибочный direct,
лишний VPN, время выбора/ремонта p50/p95/p99 и выживание существующих потоков.
Не смешивать холодные/тёплые результаты, разные провайдеры, приложения и протоколы.
Показывать как результат при наличии рабочего разрешённого пути, так и общий
пользовательский результат; исключённые случаи и неизвестные исходы видимы.

Даже 299 независимых успехов без отказа дают лишь примерно 99% нижнюю границу
вероятности при одностороннем доверии 95% для этого распределения испытаний.
Сотни коррелированных запросов к одному сайту такого вывода о всём интернете
не дают. Длительный прогон измеряет устойчивость, а не универсальную точность.

Обязательная матрица: DNS timeout/подмена/негативный ответ; отказ первого CDN-IP;
нерабочий IPv6; TCP reset до/после ClientHello; неверный сертификат; H2/H3/ECH;
403/429/5xx; блокировка UDP/одного IP; MTU black hole; потери/задержка/перегрузка;
idle WebSocket/UDP; исчезновение сети; смена NIC/профиля; sleep/resume; старый PID
или поколение; Stop во время выбора; переполнение IPC; смерть моста/DPI/policy;
Tailscale SSH/MagicDNS/subnet routes/exit node; старт SYSTEM до входа; обновление,
откат и удаление. Проверять одновременно direct, VPN-only, видео, голос и игру.

Текущая старая Windows 10 VM — только один стенд. Нужны актуальная Windows 11
с включёнными штатными защитами и второй физический ПК/другая сеть. Конкретный
список поддерживаемых Windows и WireSock фиксируется по результатам, а не по
одному факту успешной сборки. Тесты с реальной сменой физических сетей не
заменяются одной NAT-ВМ.

Ресурсы сравнивать на одинаковом оборудовании и нагрузке после прогрева: CPU,
private bytes/working set, дескрипторы, сокеты/порты, очередь, записи на диск и
диагностический трафик. Добавить плотную нагрузку и 12–14 ч; фиксировать тренд,
а не только конечное число. Численные бюджеты утверждаются по базе 0.6.0 и
целевой слабой машине до включения новой функции по умолчанию.

Условия стабильного выпуска: нет известных критических регрессий; нет повторных
прикладных операций; соблюдены запреты в контролируемом захвате; отказ и Stop
заканчиваются в заданном бюджете; проходят установка/обновление/удаление;
показан выигрыш против базы без нарушения бюджета ресурсов. Сначала режим
наблюдения, затем отдельный пилот, затем включение по умолчанию. Откат
экспериментальной функции не снимает обязательное правило VPN-only.

## Ближайший объём работ

Следующий небольшой выпуск: подтверждённые исправления по длительным логам,
структурированные причины и измерения, несколько DNS-адресов/резерв разрешения,
регрессионные тесты текущей цепочки. Ранний выбор и новый транспорт первоначально
поставляются отдельными экспериментами. Номера выпусков назначаются после
приёмки объёма; relay и дополнительный пакетный драйвер не входят автоматически
в ближайший патч.

Дополнительная приёмка: [массовая проверка доступности](REACHABILITY-LAB.md) —
версионированный корпус Tranco/тематических списков, локальные пробы по путям,
выборочное сравнение с OONI/Globalping и независимый контроль. Сначала 500–1000
целей, затем расширение по бюджету стенда. Длительный тест устойчивости сначала
проводится отдельно, чтобы нагрузка измерителя не скрывала причину отказа.
До реализации быстрого выбора полезен независимый архитектурный аудит;
задание и требования к доказательствам включены в тот же документ.

Компактный интерфейс сохраняет одну кнопку, профиль и короткий статус:
«Подключение», «Проверка сети», «Выбор пути», «Восстановление VPN», «Нет сети».
В расширенном режиме видны причина, область отказа, выбранный путь и свежесть
доказательств. Рекомендованный пресет должен работать без ручного понимания DNS,
транспортов или DPI. Android остаётся отдельной будущей платформой.
