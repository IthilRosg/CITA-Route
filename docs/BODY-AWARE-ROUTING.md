# Проверка тела HTTP в Auto — кандидат после 0.6.3

## Реализация

PolicyOptions.VerifyBody=true по умолчанию, независимо от браузерного адаптера.
Lists не запускает адаптивную калибровку. При VerifyBody=false сохраняется старая
HEAD-проверка; переключение режима требует переподключения. Стратегия ключа
обновлена до tls-record-ipv4-body-v4; кэш и снимки активных путей разделены также
по BodyProbes, чтобы старые проверки не выдавались за новые.

Кандидаты используют собственный GET https://domain/ с нормальным TLS и адресом,
проверенным независимым публичным DNS каждого пути. Cookies/авторизация браузера
не передаются; редиректы не следуются, пользовательские запросы не воспроизводятся.
У каждого пути две отдельные пробы, память чтения 4 КиБ, максимум 64 КиБ на пробу,
общий бюджет подключения/запроса прежние 3 с, idle чтения 1,2 с. Не вводится
правило по точной отметке 16 КиБ: допускается любая повторяемая остановка тела.

Уровни: Headers, BodyComplete, BodySample, BodyUnknown, BodyIncomplete,
BodyStalled, BodyBudgetExceeded. Маленький EOF — полное маленькое тело;
64 КиБ — только ограниченная выборка, не весь файл. Глобальный бюджет не
приравнивается к отсутствию прогресса. 403/redirect корня сохраняют лишь прежнее
свидетельство заголовков, не объявляют проверенными изображения/CDN.

Два частичных stall у пути дают ApplicationFailure. Mixed/неопределённые
результаты не становятся стабильным подтверждением. По-прежнему две параллельные
калибровки контроллера, direct/DPI/VPN проверяются параллельно, каждая проба
закрывает свои потоки. Новая публикация ожидает подтверждения движка. Стабильность
возврата к предпочтительному пути сохраняется. Headers не продлевает TTL и не
заменяет BodyComplete/BodySample решения того же ключа.

Оценка верхней границы трафика: до 384 КиБ за калибровку домен+процесс (3 пути ×
2 пробы × 64 КиБ), обычно меньше из-за отмены ненужных путей. Это не лимит на
секунду и не измерение реальной нагрузки; queue/rate/cache ограничения прежние.
Не выполнять такие проверки для каждого пакета или всех доменов Интернета.

## Первый запрос изображения

BrowserFeedbackWatch теперь сохраняет время начала ресурса и его опубликованную
revision. Новый body-подтверждённый маршрут, опубликованный после начала запроса,
может разрешить уже существующий механизм ОДНОГО повтора точного неподписанного
изображения, даже если собственная проверка закончилась раньше browser error.
Проверки session/bridge generation, возраста, Manual/pinned, свежести решения,
подтверждения движком, fingerprint и browser ownership сохраняются.
Headers, старая revision или proof до начала ресурса повтор не разрешают.
Сам повтор остаётся в images.js: без query/hash/srcset/picture, без POST/XHR,
только совпадающее failed Image; успешные/отменённые/удалённые не воспроизводятся.

Этот механизм не переносит TCP-поток и не обещает спасение первого Document.
Браузер может продолжать уже начатую передачу по старому соединению, а backend
может иметь непредставительный root. Это отдельные ограничения и gates.

## Исправление запоздалой ошибки первого ресурса

Первый cold-run выявил точную гонку: ошибка Image пришла после изменения
published revision. Старый Fail правильно отклонял её как устаревшую, но не
оставлял возможность безопасного повтора. Добавлена отдельная ветка
WatchBrowserFailure для Image: stale failure не регистрируется как сбой нового
пути, не изменяет quarantine и не запускает калибровку заново. Она может создать
только repair watch, если уже существует live BodyComplete/BodySample решение,
полученное после старта исходного ресурса, и подтверждённая новая publication.
Все существующие session/bridge/age/Manual/pinned проверки остаются; для poll
по-прежнему требуется Applied и сравнение resource revision.

Runtime-кандидаты body-next-single/body-next-tested — промежуточные; окончательный
для текущего прогона — runtime/body-next-final/RoutePilot.Agent.exe. На ВМ он
установлен штатно с резервной копией. Финальный self-test этого образа прошёл;
GUI build прошёл; JS-проверки прошли. Отдельный legacy cache fixture теперь
явно отключает VerifyBody, чтобы тестировать старый режим, а не выдавать старый
кэш за новое body-доказательство. Новый набор сочетаний VerifyBody/FastTcp
проверяет отбрасывание кэша при изменении любого режима.

Первые холодные результаты сохранены в body-auto-before-retry.json и
body-auto-before-late-error-fix.json. Они не подтверждают восстановление первого
документа Windows64 или всех изображений; следующий тёплый запрос Windows64 уже
получал 53 собственных изображения через автоматически выбранный VPN.

## Повтор исходного URL и предел холодного захода

Отдельный последний collector добавляет тот же windows64 раздел в конец той же
сессии. У первого варианта повтор не измерен из-за ExtensionCommand до навигации;
отчёт сохранён body-auto-repeat-popup-failure.json, его success=false не является
доказательством отказа сайта. Первые четыре страницы при этом измерены, четыре
изображения Ryuugames восстановлены, правила/сессия корректно остановлены.

Для повторного контроля (пятая страница) native extension теперь намеренно не
подключается: это независимая проверка нового потока по уже рассчитанной политике.
В отчёте adapter=null, adapterSkipped=true; фикстура исключает такой контроль из
критерия connected адаптера, но completed по-прежнему требует измерения всех
пяти страниц. Первые четыре страницы сохраняют полный native/pipe/controller путь.
Это исправление измерителя, не обход проверки канала и не изменение клиентского UX.

Полностью бесшовное спасение первого Document/блокирующего Script ещё не выполнено.
Подтверждённый новый маршрут применяется новым соединениям, а существующие TLS-
потоки не переносятся. Возможные следующие решения требуют отдельной приёмки:
приоритетная калибровка до выпуска первого потока (ограниченный first-use gate)
или понятное предложение обновить документ. Автоматически переповторять main-frame,
скрипты, POST, подписанные запросы или уничтожать TCP недопустимо без точного
механизма безопасности и проверки пользовательского контекста.
