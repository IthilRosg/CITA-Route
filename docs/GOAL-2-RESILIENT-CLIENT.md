## Результат

Самостоятельный Windows-клиент: установка, импорт своего WG/AWG-конфига,
одна кнопка подключения, автоматический выбор из трёх реализованных путей,
достоверный статус и восстановление после отказов. WireSock не требуется.
Готовность доказывается поведением конкретной сборки на физической РМ.
Наличие кода, лабораторного селектора или открывшейся главной страницы
не считается завершённой интеграцией.

## Порядок и критерии

1. **Воспроизводимая основа.** Собрать текущие app/agent/native, выполнить
   релевантные self-tests, определить точные артефакты и хеши. Сохранить
   имеющиеся изменения; не откатывать рабочее дерево целиком. Исправлять
   подтверждённые отказы, отделяя ограничения среды теста от дефекта продукта.
2. **Базовый пользовательский цикл.** Проверить EXE-установку на РМ,
   отсутствующий/имеющийся .NET, импорт валидного и отказ невалидному профилю,
   подключение, отключение, повторный запуск, сохранение профиля и
   автоподключение при запуске. Проверить обновление и предупреждения для
   той же/старой версии, отмену и откат. Не заменять установленный клиент
   на основном ПК и не удалять пользовательские профили.
3. **Производственный путь Zapret.** Проверить актуальный Windows upstream,
   лицензию, происхождение/целостность компонентов и требования драйвера.
   Реализовать управляемый жизненный цикл, адресные/протокольные области,
   проверку готовности, остановку и очистку. Проверить сосуществование
   WinDivert/WFP/TUN и стороннего обходчика. Не отправлять внешний VPN-транспорт,
   локальное управление и исключённые сети повторно в обработчик. Ошибка драйвера
   должна давать понятный отказ конкретного пути. Лабораторная TLS-фрагментация
   не заменяет интеграцию Zapret.
4. **Автоматический выбор трёх путей.** Проверять конкретные сочетания
   приложение/назначение/протокол с ограниченными бюджетами, TTL и поколением
   сессии. Использовать независимые DNS/TLS-проверки без повторной отправки
   пользовательских запросов, POST, токенов и содержимого сессий. Сертификат,
   HTTP 403/429 и ошибка авторизации сами по себе не доказывают блокировку.
   Различать TCP/HTTPS, QUIC/UDP и медиа; успех одного не разрешает все остальные.
   Соблюдать принудительные правила пользователя и защиту: отказ VPN не
   разрешает незаметный Direct для трафика, который должен идти через VPN.
5. **Отказоустойчивое применение.** Атомарно согласовать решения с защитой;
   закреплять путь существующих потоков, применять новые решения к новым.
   Проверить смерть/зависание модуля, потерю сервера/DNS/сети, смену интерфейса,
   сон/возобновление, смену профиля и отмену операции. Ограничить повторы,
   применять backoff и защиту от частых переключений. Ручное отключение
   сохраняет намерение пользователя. Не обещать сохранение TCP/звонка при
   изменении внешнего IP/NAT: это отдельное измеряемое ограничение.
6. **Интерфейс и ресурсы.** Компактный режим: профиль, подключение, небольшой
   статус/статистика; расширенный — причины решений и диагностика. Показывать
   настройку, проверку, восстановление, частичную доступность и ошибку пути,
   не выдавая поднятый процесс за доступный интернет. Убирать устаревшие
   сообщения по поколению операции. Ограничить CPU/RAM/число проб, объём кэша,
   логов и параллелизм; сбор содержимого трафика не требуется.
7. **Приёмка тестового выпуска.** Один идентифицированный пакет проходит
   пользовательский цикл и матрицу отказов на физической РМ, проверки всех
   трёх путей, локального/Radmin/Tailscale-доступа, HTTPS, загрузок и
   синтетического UDP/медиа под нагрузкой. Для реального RF-обхода требуется
   отдельное сетевое подтверждение; синтетический фильтр подтверждает только
   логику. Сохранить метрики до/после, остатки временных правил/процессов = 0,
   ограничения и известные проблемы. Затем собрать кандидат установщика.

## Запись этапа: динамическое исправление, 29 октября 17:26 МСК

На физической РМ подтверждено устранение конкретного WFP/WinDivert конфликта.
Для System добавляется только тот же exact tuple (оба IPv4, local port,
remote 443, TCP, physical LUID). Допуск требует уже существующего разрешения
этого tuple агенту. Новый режим ограничен UUID физической станции и путём
защищённого lab helper, не объявляется штатным Plan и не включён publisher.

Разрешение непостоянное: отдельная dynamic WFP session живёт вместе с helper,
закрывается по EOF, смерти процесса или лабораторному watchdog 20 s.
После закрытия отдельный helper независимо проверяет отсутствие System-правила;
проверка не требует доступности прежнего NIC. Исходный сокет остаётся удержанным
до окончания этой проверки. Семантика удаления объектов dynamic session описана
Microsoft: https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_session0

Наблюдатель выявил ошибки lost/partial ACK и malformed ACK: отменяемое чтение
могло потерять часть строки или помешать независимой проверке cleanup.
Исправлено: сохраняется одна задача чтения, отменяется только ожидание,
после exit ошибки ответа не заменяют проверку отсутствия kernel-правила.
Отмена самой проверки по-прежнему не означает успешную очистку.

Последовательное сравнение ОДНОЙ финальной сборки:
- без companion — Connecting timeout, TLS=false (исходный дефект воспроизведён);
- с companion — Go pipe → guard → Zapret → TLS validation=true, HTTP403;
- LostAckReleased=true после уже выполненного grant;
