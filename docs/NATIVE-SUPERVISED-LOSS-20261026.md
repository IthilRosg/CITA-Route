# Короткие потери с владельцем восстановления — 26 октября 2026

## Что проверяется

Продолжение `NATIVE-SHORT-LOSS-20261026.md`: те же 500/2000/10000 мс,
двусторонняя потеря и только входящие, но с coordinated native owner и его
настоящим циклом HTTPS/UDP, подтверждением отказа и общим бюджетом ремонта.
TCP идёт через кандидатное ядро и локальный аутентифицированный транспорт.
Это проверка механизма владельца, не установленной C#-службы и не OS TUN.

Инъекция действует ниже шифрования по монотонному таймеру и сохраняется после
Rebind. Она не меняет socket/netstack сама и не может искусственно сделать
ремонт успешным снятием блокировки при смене порта. Основная сеть не меняется.

## Границы лабораторного управления

PauseChild разрешён только coordinated-владельцу с явным флагом
`CITA_NATIVE_SHORT_LOSS_LAB=1` и при выключенном persistent control.
Дочерний транспорт повторно проверяет флаг, принадлежность команды,
длительность из allowlist и однократность инъекции. Установленный persistent
control отклоняет потерю даже при ошибочно переданном лабораторном флаге.
Новых TCP-портов управления и загрузки конфигов через журналы нет.

Ремонт, его пороги и таймеры не изменены. Пересылка команд к дочернему процессу
сохраняет прежние блокировку, срок, ограничение кадра и проверку ответа.
Go unit tests/vet и синтаксические проверки PowerShell прошли.

## Свежесть и наблюдения

Стенд опрашивает состояние примерно раз в 500 мс во время GET. Сохраняются
elapsedMs, health, epoch, socketRepairs, restarts и исходы последней пробы.
Это дискретные наблюдения, не точные моменты начала/окончания ремонта.
Успех требует новой успешной HTTPS/UDP-пробы с временем завершения после
заданного окна потери, того же поколения, отсутствия перезапуска child,
фактических отброшенных пакетов и сохранённого TCP (dials 1→1, reused=true).

Первый прогон `native-awg-short-loss-4f9a6d7c2b9f47339aad34f28f5b9e44.json`
сохраняет предварительные наблюдения. При 0,5/2 с ремонтов не было; при 10 с
был один ремонт, TCP сохранён. После него уточнён критерий свежести, чтобы
прежняя Reachable-проба не засчитывалась подтверждением восстановления.
Подробные JSON сохранили исходы проб; ограничение глубины затронуло только
краткую консольную печать, её глубина также исправлена.

Финальная квитанция:
`runtime/native-awg-short-loss-9481f3b849ff4287999117d3d8ae9ba7.json`.
Шесть сценариев успешны: свежие HTTPS/UDP после окна потери, TCP сохранён,
epoch=1, child restarts=0, хеши совпали, очистка/топология подтверждены.

| Потеря | Двусторонняя: GET, мс / ремонты | Входящие: GET, мс / ремонты |
|---|---:|---:|
| 500 мс | 944 / 0 | 930 / 0 |
| 2000 мс | 3357 / 0 | 3979 / 0 |
| 10000 мс | 12957 / 2 | 16461 / 1 |

В отличие от предварительного прогона, 10-секундная двусторонняя потеря
потребила два ремонта вместо одного. Оба прогона сохранили TCP; первый GET
занял 12957 мс в обоих случаях. Сдвиг относительно health-цикла влияет на
решения; статистического сравнения фаз пока нет. Эта матрица подтвердила
избыточную повторную попытку в данном сценарии, но не ускорение.

Следующая целевая доработка: интервал между повторными ремонтами в пределах
непрерывной недоступности с отдельной проверкой нового сбоя после успешного
восстановления. Слишком большой интервал способен замедлить полезную повторную
попытку, поэтому значение выбирается сравнением обрывов и настоящего blackhole,
а не переносится в основную установку по одному измерению.

## Воспроизводимость и ограничения

Отдельный архив `runtime/native-supervised-loss-source.zip` воспроизвёл все
три компонента без сетевой загрузки, из включённого module proxy.
Source SHA-256: 673FB520EC4F37BA83798278639AA4E1528488B299E346D5EA95E8D5F5077720.
Owner SHA-256: 3C7E92A7B45F800FE7FAE9411C2C3F90F91EEA578D83F8060BA627560FD6C516.
Core и guard не изменены относительно предыдущего этапа.

По одному наблюдению на ячейку и историческому базису нельзя доказывать
ускорение, P95 или отсутствие лишнего ремонта при любой фазе сбоя.
Временная недоступность общего выхода может не лечиться сменой локального
UDP-порта. Отдельная исходящая потеря, независимые адреса контроля, сдвиги
относительно health-цикла, UDP-нагрузка и интеграция со службой остаются дальше.
Настройки автоматического восстановления в основной установке не менялись.
