# Веб-ресурсы, частичная передача и QUIC

Дата: 2026-10-22. Итерация поверх `279fe04`, ещё не установлена на основной ПК
и не заменяет исполняемые файлы длительного пилота в ВМ.

## Воспроизведение в ВМ

Публичная страница, указанная пользователем, загружена собственным анонимным
GET, без выполнения JavaScript, входа, перехода по рекламным цепочкам и скачивания
архивов. Из HTML извлечены адреса изображений; проверено не более шести ресурсов,
до 512 КиБ каждого на путь. Содержимое изображений не сохранялось и не анализировалось.

| Ресурс | Direct | VPN |
|---|---|---|
| `srnky.com/` | HTTP 200, HTML получен | HTTP 200, HTML получен |
| Указанная короткая ссылка srnky | HTTP 200, затем таймаут чтения | HTTP 200, первые 64 КиБ получены; лимит, не весь документ |
| JPEG с `p.inari.site`, первый | HTTP 200, 23 983 байта, таймаут | 125 632 байта, EOF, полностью |
| JPEG с `p.inari.site`, второй | HTTP 200, 29 183 байта, таймаут | 136 509 байт, EOF, полностью |
| Обложка с домена Ryuugames | Таймаут | HTTP 200, все 64 106 байт |
| Два проверенных JPEG Steam CDN | HTTP 200, EOF, полностью | HTTP 200, EOF, полностью |

Ещё один JPEG Steam больше лимита: первые 512 КиБ получены обоими путями,
полная передача не проверена. Первые наблюдения — 16:47:29–16:47:58 МСК;
HTML/изображения — 16:55:31–16:55:49. Эти интервалы нельзя выдавать за простой
клиента при анализе ресурсов длительного теста.

Все эти пробы используют HTTPS/TCP. Ошибка QUIC на снимке браузера — отдельное
наблюдение, не доказательство причины каждого воспроизведённого отказа TCP.
`ERR_BLOCKED_BY_CLIENT` также отделяется: по определению Chromium запрос блокирует
сам клиент. Возможны расширение или иная клиентская политика; автоматически
объявлять это блокировкой провайдера и отключать расширения нельзя.
[Список ошибок Chromium](https://github.com/chromium/chromium/blob/main/net/base/net_error_list.h),
[диагностика протоколов Cloudflare](https://developers.cloudflare.com/speed/optimization/protocol/troubleshooting/protocol-troubleshooting/).

## Общие изменения

1. **Первое использование домена.** В Auto контроллер ставит новый фактически
   наблюдаемый HTTPS-домен приложения в очередь собственных проверок, включая
   короткие потоки из журнала. Не требуется сначала дождаться браузерного таймаута.
   Маршруты общего CDN не наследуются от страницы и не переводят весь браузер в VPN.
   Для каждого app/domain остаются отдельные проверки и ручные приоритеты.
   Имена Tailscale `*.ts.net`, процессы Tailscale/WireSock и собственные сетевые
   компоненты исключены из обнаружения и сигналов ошибок, чтобы не адаптировать
   транспорт, от которого зависит сам VPN или доступ к overlay.
2. **Ограничение нагрузки.** Очередь discovery — 64 записи, память последних имён —
   512, начальный бюджет — четыре новых домена, затем до 20 в минуту. Проверки
   используют прежний общий предел в две одновременные калибровки. Явные ошибки
   и обновление действующих маршрутов приоритетнее discovery; очередь устаревает
   через две минуты. Калибровка может выполнять несколько независимых HTTPS-проб,
   поэтому 20 доменов не означает 20 сетевых запросов.
3. **Ошибка после получения заголовков.** Разбираются настоящие сообщения движка
   `connection upload/download closed:`, а не только отказ открытия соединения.
   Две ошибки разных потоков app/domain на одном пути за 90 секунд временно
   понижают его на три минуты. Один поток не считается двумя подтверждениями из-за
   повторной записи; обычная отмена пользователем исключается. Это не диагноз DPI.
   Даже если главная отвечает HTTP 200, альтернатива требует двух собственных
   успешных HTTPS-проб. Ошибка сертификата по-прежнему останавливает адаптацию.
   История ограничена и видна в `policy-state.webFaults`.
4. **Адресная веб-совместимость QUIC/TCP.** Для наблюдённого UDP/443 известного
   браузера и свежего подтверждённого TCP-пути DPI/VPN формируется правило новых
   соединений app/domain/443. Внешнее правило движка дополнительно требует
   распознанный QUIC: другие UDP, включая тот же домен и порт, не отвергаются.
   Положительное решение о TCP не считается проверкой качества QUIC. Правило
   исчезает при direct, устаревшем подтверждении, ручном приоритете или очистке.
   Неизвестные приложения и игры не принуждаются к TCP. При старой или смешанной
   топологии функция отключена: новый worker сам по себе не меняет смысл старого
   `auto-blocked`. Существующие соединения не мигрируют и не разрываются.
5. **Проверка тела ресурса.** `--check-web-resource <root> <https-url>` выполняет
   только явно запрошенный анонимный GET на каждом пути, до 512 КиБ, без cookie,
   авторизации, переходов и изменения правил. Окончание тела, лимит выборки и
   таймаут после части данных различаются. DNS проверяется отдельно для пути,
   публичный IPv4 закрепляется, исходное имя проверяется TLS. Путь хранится хэшем,
   содержимое не сохраняется. URL с учётными данными, query, fragment, нестандартным
   портом или локальным именем не принимается. Это инструмент диагностики, не
   фоновое повторение действий пользователя. Экспорт диагностики включает только
   известные поля отчёта; полные URL и посторонние поля не переносятся в ZIP.

Поле protocol не поддерживается в headless rule set: оно вынесено во внешнее
правило маршрутизации. Процесс, точное имя, UDP и порт остаются внутри набора.
Подтверждение загрузки новой версии набора выполняется штатной canary-публикацией.
[Правила маршрутизации](https://sing-box.sagernet.org/configuration/route/rule/),
[headless rules](https://sing-box.sagernet.org/configuration/rule-set/headless-rule/).

## Проверки кандидата

Самопроверки агента прошли на основном ПК и в ВМ. Покрыты лимиты discovery,
дедупликация и срок ошибок, смена пути при здоровом корне, отказ при ошибке
сертификата, очистка, ручные правила, срок TCP-подтверждения и смешанная топология.

В ВМ пройден изолированный стенд с настоящим движком: публичный одиночный QUIC
ClientHello до правила доходил до собственного loopback-приёмника, после
подтверждённой canary-публикации — отвергался; обычный UDP того же app/domain/443
продолжал доходить. Снятие правила вернуло новые QUIC-потоки. Действительная
идентификация процесса включена; UDP-сокет стенда использует номер исходного
TCP-порта SOCKS control, соответствующий метаданным mixed inbound.
Стенд воспроизводится `Test-WebRouting.ps1`; публичный пакет извлекается из
закреплённого исходного архива sing-box, проверяется SHA256, пользовательский
трафик не захватывается. Все выходы принудительно направлены на loopback.

Отдельно пройдены 30 переходов VPN/DPI на настоящем движке с сохранением уже
открытого TCP, проверки подтверждения правил, отказа записи, потери ack и смены
поколения. Действующая сессия длительного пилота и поколение не менялись.
Повторные изолированные проверки выполнялись в интервале 17:06–17:26 МСК;
этот период также не является измерением полностью простаивающего стенда.

Новый `--check-web-resource` проверен в ВМ в 17:13:35–17:13:52 МСК: для JPEG
`p.inari.site` direct и DPI получили HTTP 200 и около 25 КБ, затем истёк срок;
VPN получил все 125 632 байта за 491 мс. Для srnky direct/DPI также остановились
примерно на 23,5 КБ; VPN получил лимит 512 КиБ за 1263 мс. Это корректно
отмечено как частичная передача и ограниченная выборка соответственно,
а не как полная загрузка страницы. Кандидат не применял новые правила пилоту.

## Границы и следующая приёмка

Сам факт прихода байтов не подтверждает полную загрузку изображения. Шифрование
не позволяет сетевому контроллеру узнать ожидаемый размер, HTTP/2 stream id или
ошибку конкретного изображения. Молчаливое зависание после части ответа и обычная
отмена браузером могут выглядеть одинаково; принуждать каждый простаивающий
keep-alive/WebSocket к VPN нельзя. Обычная автокалибровка всё ещё проверяет корень
домена, а не повторяет исходный пользовательский URL. Не все случаи из таблицы
тем самым автоматически исправлены.

Для дальнейшего покрытия нужен отдельный браузерный канал наблюдений: ошибки
загрузок и ресурсов, редиректы, протокол и только необходимые домены/типы запросов.
`ERR_BLOCKED_BY_CLIENT`, отмены, HTTP 403/challenge и сетевые отказы должны оставаться
разными категориями. Канал требует проверки подлинности и ограничения частоты;
cookie, токены, полные URL с параметрами и содержимое не передаются. Автоматическое
повторение POST, платежей, сообщений и отправки форм не допускается. Повтор
безопасной загрузки GET должен инициировать сам браузер. Это отдельный этап,
а не заявленная выполненная часть этой итерации.

Перед выпуском обязательна проверка браузера через настоящий TUN: сломанный QUIC
при исправном TCP, переход на HTTP/2 или HTTP/1.1, повтор картинки и загрузки,
сохранение старых TCP, UDP игр/голоса, ручные исключения и обратный переход.
Проверка SOCKS/UDP на настоящем движке подтверждает правило, но не поведение
браузера и не доступность всех внешних сайтов. Текущий 12-часовой пилот использует
другую сборку и не засчитывается как длительная приёмка этого кода.
