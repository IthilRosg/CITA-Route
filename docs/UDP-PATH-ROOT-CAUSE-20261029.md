# UDP: локализация причины, 29 октября 2026

## Подтверждено

Потери воспроизводятся без CITA Route и без WireGuard: обычный Linux UDP-сокет на SE отправляет тестовые пакеты в DE-2, но при 50 пакетах/с возвращается около 8 ответов/с. Изменение нативного bind RIO на StdNet этого симптома не устранило. Это не доказывает отсутствие любых дефектов клиента; оно исключает обязательное участие клиента в воспроизведённом ограничении этого межсерверного потока.

Контролируемые адреса: SE 138.124.250.203, DE-2 143.20.37.241. Измерения проводились в ночь 29 октября по Москве. Ограниченные временные ответчики проверяли случайный тестовый маркер, принимали только разрешённые IP и отвечали пакетом того же размера. VPN-ключи и содержимое пользовательского трафика не записывались.

| Опыт | Отправлено | Принято клиентом | Значение |
|---|---:|---:|---|
| CITA RIO, 50 pps, 60 с | 3000 | 480 | Симптом воспроизведён |
| SE → DE, Linux UDP, 50 pps, 20 с | 1000 | 160 | Симптом есть без CITA |
| SE → DE, Linux UDP, 4 pps, 20 с | 80 | 79 | При малой частоте почти нет потерь |
| SE → DE, Linux UDP, 16 pps, 20 с | 320 | 152 | Пропускная частота близка к 8 pps |
| SE → DE, другой порт 49215, 50 pps, 20 с | 1000 | 160 | Не ограничено одним тестовым портом |
| DE → SE, Linux UDP, 50 pps, 20 с | 1000 | 160 ответов на DE | SE принял и отослал все 1000: дефицит на направлении SE → DE |

Все приведённые выше пакеты имели UDP payload 224 байта. Предел в пакетах в секунду пока нельзя путать с лимитом байтов в секунду: сравнение размеров записывается отдельно.

Дополнительная матрица, `runtime/se-udp-size-flow-matrix.jsonl`: при 50 pps пакеты 96 и 1024 байта дали по 159 ответов из 1000 за 20 секунд. Два одновременных потока с разными исходными UDP-портами дали 160 и 159 ответов из 1000 каждый (319 суммарно). Дельты SE qdiscDrops/txDropped/txErrors за матрицу равны нулю. Это сильное свидетельство packet-rate ограничения отдельного потока, а не общего лимита пропускной способности/IP. Точное правило и владелец по-прежнему не установлены.

## Точки наблюдения

В одном 60-секундном прогоне CITA внешний интерфейс SE увидел 3000 запросов к DE и 480 ответов. Входной capture DE увидел 480 запросов и 480 ответов. Для входящих пакетов DE контрольные суммы UDP корректны. Дельта `/proc/net/snmp` DE: InDatagrams=480, OutDatagrams=480; InErrors, RcvbufErrors, InCsumErrors, SndbufErrors, MemErrors = 0.

На SE внешнем capture: 3480 captured/3480 received by filter, 0 dropped by kernel. На DE: 960 captured/961 received by filter, 0 dropped by kernel. Неучтённую строку DE нельзя считать доказанным сетевым пропуском. Захват туннельного интерфейса SE в этом опыте записал 2998 запросов и 480 ответов; поэтому точный счёт 3000 берётся из внешнего capture, не из этого туннельного файла.

При обратном опыте ответчик SE принял 1000 корректных запросов от DE и успешно вызвал sendto 1000 раз, без отказов source/length/auth. На DE вернулись только 160. Успех sendto не доказывает физическую отправку каждого ответа, но согласуется с прямым опытом и внешним capture.

Проверенные nftables/iptables/legacy правила не содержат UDP packet policer для этого потока. Найденные `limit 3/min` относятся к UFW logging; принимать их за ограничение UDP нельзя. На DE нет видимого XDP attachment, а показанные очереди и интерфейс не имеют счётчиков потерь. Накопленные drops очереди SE сами по себе не являются дельтой теста и не объясняют порог без отдельного сравнения.

## Что остаётся гипотезой

Самый узкий подтверждённый участок потери — после точки наблюдения внешнего интерфейса SE и до точки наблюдения входного интерфейса DE. Сюда входят инфраструктура виртуализации, маршрутизаторы и внешние фильтры. Точное устройство, правило и владелец ограничения пока неизвестны. Признаки rate policing сильные, но термин «8 pps limiter» пока описывает наблюдаемое поведение.

Freakhosting публично указывает внешнюю DDoS-фильтрацию Dataforest/CosmicGuard: https://freakhosting.com/ddos-protection/. Это делает такой фильтр проверяемой гипотезой, но не доказывает применение конкретного правила к DE-2.

## Условия завершения расследования

1. Установить конкретный механизм: внешнее правило/ограничение или иная причина, подтверждённая сопоставлением точек наблюдения и контролируемым изменением одного условия.
2. В разрешённой области устранить его либо получить соответствующее изменение у оператора; общий рабочий VPN основного ПК сохраняется.
3. Повторить тот же Linux UDP baseline до/после и прогон CITA с той же нагрузкой; оценивать loss, burst, задержку и ошибки стенда.
4. Если внешняя сеть исправлена, а дефицит CITA остаётся, продолжить локализацию клиента. Не объявлять остальные проблемы клиента исправленными по межсерверному тесту.
5. Удалить временные правила и процессы, проверить восстановление профиля и бинарных файлов РМ. Цель до этого остаётся активной.
