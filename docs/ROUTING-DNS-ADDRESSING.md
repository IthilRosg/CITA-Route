# DNS и резервные IPv4-адреса

Дата: 2026-10-21. Рабочая ветка: `codex/routing-measurements`.
Изменения находятся в исходниках и изолированной сборке для ВМ; установленная
версия основного ПК и опубликованная 0.6.0 не заменены.

Это ограниченная часть этапа 2 [плана развития](ROUTING-DEVELOPMENT-ROADMAP.md),
после [базовых измерений](ROUTING-MEASUREMENTS.md). Полный этап 2, Happy Eyeballs
и согласование всех браузерных DNS/TLS-профилей завершёнными не объявляются.

## Что изменено

Раньше действующий `SelectResolved` проверял только первый IPv4 после одного
DoH-провайдера на каждом пути. Наличие двух провайдеров в отдельной функции
`Resolve` не обеспечивало резервирование этого рабочего пути.

Теперь контроллер и конфигурация движка используют одинаковый порядок:
основной Cloudflare, запасной Google. Запрос к каждому ограничен 1500 мс;
резерв включается при транспортном отказе, таймауте, SERVFAIL или REFUSED.
Корректные NXDOMAIN и NODATA завершают операцию без запроса ко второму провайдеру.
Проверка сертификатов HTTPS сохраняется.

Для direct и VPN созданы отдельные пары DNS-транспортов. Их запасные запросы
идут через тот же выход, что основные. Direct и DPI в контроллере используют
один direct DNS-результат; VPN получает собственный результат. Конфигурация
обычного подключения и подготовка автономной диагностики обновлены вместе.
Транспорты FakeIP и Tailscale не заменяются этой настройкой.

В закреплённом движке 1.14.3 кэш уже разделён по тэгу DNS-транспорта.
Это существующее свойство, подтверждённое тестом, а не исправленный дефект.
Устаревший параметр `independent_cache` не добавляется.

В движок добавлен небольшой DNS-транспорт `cita-fallback`, объединяющий два
существующих транспорта с отдельным сроком каждой попытки. Он не устанавливает
службу или драйвер, не перезапускает сеть и не записывает имена запросов в журнал.
Зависимости транспорта проверяются штатным менеджером движка. Модификация
помечена версией `1.14.3-cita.2`; сборка включает соответствующие исходники,
лицензии и проверки контрольных сумм исполняемого файла и архива исходников.

## Граница перебора адресов

Контроллер последовательно проверяет до четырёх различных публичных IPv4 из
ответа, с общим сроком до 3 секунд на раунд. Два независимых раунда существующей
проверки маршрута сохранены. Частные/служебные ответы не используются для проб.

Продолжение на следующий IP разрешено только при недоступности TCP. После
успешного TCP результат TLS/HTTP завершает попытку; ошибка сертификата сохраняет
прежнюю консервативную политику. Это не даёт объявить путь рабочим по второму IP,
если настоящее приложение уже подключилось к первому и получило отказ позже.

Реальный движок уже умел последовательно пробовать несколько IP до установления
TCP; его механизм передачи пользовательских данных не заменяется. Интеграция
подтверждает согласованность для быстрого TCP-отказа первого адреса.
При чёрной дыре на первом IP весь срок может закончиться на нём. Параллельный
перебор, отдельный срок каждого TCP и адресная история требуют следующего этапа.
Не заявляется, что совпадают абсолютные сроки контроллера и движка, весь набор
адресов или их поведение при любых отказах.

Произвольный IP приложения не переписывается по догадке о домене. Уже отправленные
пользовательские байты не повторяются. IPv6, HTTPS/SVCB, ECH и собственный DoH
браузера требуют отдельных сценариев; этот шаг реализует только ограниченный
IPv4-случай существующей калибровки.

## Проверки в CITA ROUTE TEST LAB

Использован существующий гость Windows 10, с проверкой UUID VMware и SHA-256
переданных файлов. Проверяется отдельная лабораторная сборка; установленный
клиент и обычная отключённая сессия сохраняются.

- Нативные Go-тесты: обычный и отрицательный ответы, SERVFAIL/REFUSED, срок
  отдельной попытки, Stop без запуска резерва, неизменность вопроса между детьми.
- Полный набор самопроверок агента: успешно, 29,6 с; дополнительно проверены
  рабочий вызов DNS-резерва, отрицательные ответы, отмена, уникальность/предел
  адресов, отсутствие перебора после TCP и повторная миграция конфигурации.
- Настоящий движок: проверка итоговой HTTPS/DNS-конфигурации без её запуска;
  затем управляемые DNS и HTTP на loopback. Все 10 сценариев прошли за 3,3 с.
- Повторная интеграция переключений на обновлённом движке: успешно, 42,6 с.
  Тридцать переходов VPN/DPI сохранили открытый TCP; новые подключения следовали
  подтверждённому правилу. Повторно проверены отложенный запуск, потеря
  подтверждения, ошибка записи, Clear, смена поколения и завершение контроллера.

Десять сценариев интеграции: принятие рабочей конфигурации; резерв после SERVFAIL;
раздельный кэш одного имени для direct/VPN; TCP-отказ первого IP; один запрос
приложения на подключение; NXDOMAIN; NODATA; таймаут основного DNS; отказ обоих
DNS; отсутствие повторной отправки после принятого TCP с последующим отказом.

Метки direct/VPN на этом стенде обозначают разные loopback-адреса выхода.
Они подтверждают привязку транспорта и кэша внутри движка, но не физический
перехват WireSock, реальный VPN-only или доступность внешнего домена.
Внешние доменные проверки впоследствии выполнены только внутри ВМ;
NAT и возможный VPN основного ПК учитываются в их ограничениях.
Подробности обычного подключения полной кандидатной сборки, DNS/TLS через
настоящий WireSock и восстановления установки:
[приёмка 2026-10-22](ROUTING-ACCEPTANCE-2026-10-22.md). Эти результаты дополняют
управляемые сценарии, не превращая их в доказательство физической VPN-only-границы.

Необработанные отчёты и лабораторные сборки сохраняются в игнорируемом `runtime`.
Они не включаются в публичную поставку. Полная сборка установщика и публикация
релиза в этом шаге не выполнялись.

## Дальше

Сценарий молчащего первого IP и первый ограниченный эксперимент описаны в
[ROUTING-TCP-BUDGET.md](ROUTING-TCP-BUDGET.md). Далее вводить ограниченное ожидание предпочтительного пути
под экспериментальным флагом, сравнивая новые замеры с сохранённой базой.
Первый готовый ответ не должен автоматически отменять приоритет direct,
правила VPN-only, ручные решения или проверку сертификатов.
