# Что доказано и что ещё требуется

**Исправление измерителя, 29 октября:** прежний `cleanup_receiver.py` читал `.diag` до остановки worker и мог вернуть предпоследний периодический снимок (до 10 секунд устаревания). Поле `counters` старых cleanup-артефактов само по себе не подтверждает окончательные серверные счётчики. Клиентские метрики и завершённые сетевые захваты от этой ошибки не зависят. Код теперь сначала останавливает worker и ждёт его завершения, затем читает счётчики; новый ответчик записывает `receiver_finalized`, cleanup возвращает `finalCountersConfirmed`. Для DE-WAN итоговый журнал перечитан: 2999 запросов/ответов SE вместо предварительных 2905 (`runtime/owner-de-wan-final-counters.json`). Для port-alias итог — 2355, совпадает с клиентом (`runtime/owner-de-port-final-counters.json`). Исходные артефакты сохранены без подмены.

Контрольные результаты относятся к UDP224байта,50пакетов/с, если не указано иное. Успешное завершение измерителя не считается подтверждением качества.

## STUN против обычного UDP: 09:27–09:29 МСК

Одинаковый tuple SE:49215 → DE:49214, один сокет каждой стороны, 96-байтные запросы и ответы, по 1000 пакетов за 19.98 с. Форматы в последовательности plain / STUN / STUN / plain. Во всех четырёх фазах SE отправил 1000, DE принял/ответил 160, SE получил 160. Невалидных пакетов, дублей и ошибок отправки нет. Максимальная задержка pacing по фазам 3.725/16.708/12.711/6.679 мс. Оба worker завершились exit 0, четыре фазы, ошибок очистки нет.

STUN Binding с SOFTWARE, FINGERPRINT и XOR-MAPPED-ADDRESS в ответе; кодек прошёл независимые тестовые векторы RFC 5769 для FINGERPRINT и IPv4 XOR-MAPPED. Отдельно проверены размеры и отказ при повреждении. Источники формата: https://www.rfc-editor.org/rfc/rfc8489.html и https://www.rfc-editor.org/rfc/rfc5769.html.

Следствие: замена конкретного тестового UDP на этот корректный формат STUN не изменила дефицит. Это ослабляет гипотезу о фильтрации только собственного формата измерителя, но не исключает классификацию других протоколов или портов и не доказывает конкретное внешнее правило. В тесте нет ICE, повторных передач STUN, MESSAGE-INTEGRITY, голоса или трансляции; один tuple может сохранять ранее назначенную внешнюю классификацию. Нет оснований переносить этот результат на все UDP-пути SE/DE.

Метрики: `runtime/protocol-udp-server.jsonl`, `runtime/protocol-udp-client.jsonl`. Проверка удаления правил и закрытия сокетов отдельными SSH-запросами: `runtime/protocol-udp-cleanup.json`.

## Валидный VPN на временном порту и повтор исходного контроля: 09:45–09:52 МСК

Временное PREROUTING REDIRECT на DE: ens3, только подтверждённый IP РМ 193.189.145.1, только публичный DE:49214 → действующий AWG:3081. Срок правила 150 с, удаление также при остановке ответчика. Внутренний ответчик — DE:49214 для peer 10.77.20.5; правило на ens3 не затрагивает этот внутренний поток.

Результат: клиент 2355/3000, итоговый журнал ответчика 2355 принято/отправлено, без ошибок/невалидных/дублей/перестановок. p95 доставленных 50.486 мс, максимальный разрыв 882.261 мс. Захват ens3 подтвердил фактический outer source 193.189.145.1, совпадающий с pin; 2357 входящих пакетов, включая VPN-служебные. Первые примерно 15 с — по 8/с, затем переход к 50/с без изменения клиента/правила. Внутренний захват увидел 2353 запроса (на 2 меньше финального счётчика), поэтому точность inner capture не принимается за абсолютную. Счётчик NAT запросили слишком поздно, после очистки; пустой результат не является доказательством отсутствия совпадений правила.

Повторный исходный Endpoint DE:3081: клиент и финальные серверные счётчики **1671/3000**, p95 50.49 мс, максимум разрыва 887.289 мс, без невалидных/дублей/перестановок. Исправленный сборщик вернул `receiverStopped=true`, `finalCountersConfirmed=true`, все final поля присутствуют, firewall/NAT/marker остатки 0. Первоначальная попытка повторного контроля имела неверный Target измерителя и завершилась exit 2 до трафика; исключена. Повторный валидный прогон сохранён отдельно.

Следствие: исходный 3081 теперь также показал потери, поэтому приписывать разницу только номеру порта нельзя; ранний 3000/3000 не гарантирует стабильность следующего нового потока. Временная динамика может зависеть от состояния потока, пути или транспорта. Для VPN-прогона одного DE ingress capture недостаточно, чтобы утверждать, что RM owner физически отправлял 50 outer пакетов/с в низкочастотную фазу. Следующий различающий шаг — синхронный подсчёт исходящих outer-пакетов на физическом NIC РМ и входящих на DE для одного идентифицированного потока. Отдельные обычные Linux UDP-прогоны по-прежнему доказывают, что похожий дефицит существует и без CITA, но не доказывают одинаковую причину каждого VPN-прогона.
