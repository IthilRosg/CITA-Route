# Материалы для следующей архитектуры CITA Route

Проверено: 2026-10-21. Использованы документация авторов, спецификации и
исследования первоисточников. Действующий порядок работ:
[ROUTING-DEVELOPMENT-ROADMAP.md](ROUTING-DEVELOPMENT-ROADMAP.md).

Дополнение о широком корпусе доменов, OONI/Globalping, локальном измерителе и
независимом аудите: [REACHABILITY-LAB.md](REACHABILITY-LAB.md).

Описание возможности upstream не подтверждает её наличие в нашей закреплённой
сборке, совместимость с WireSock или эффективность у конкретного провайдера.
Ниже отделены сведения источников от наших инженерных выводов.

Не устанавливать все найденные средства сразу. Сначала общий интерфейс адаптера,
один кандидат, эталонные отказы, сравнение качества/ресурсов и совместимости.
Перед распространением каждого — закрепление исходников/сборки, проверка лицензии
и обязательств по поставке производных компонентов. Документация текущего upstream
может опережать наш pinned engine; работоспособность подтверждается нашей сборкой.

## Сохранение соединений и доставка

- [WireGuard: Endpoints & Roaming](https://www.wireguard.com/papers/wireguard.pdf),
  [официальный quick start](https://www.wireguard.com/quickstart/): протокол умеет
  обновлять endpoint по аутентифицированным пакетам; keepalive нужен отдельным
  NAT-сценариям. Наш вывод — сначала проверить сохранение WG/AWG при смене внешней
  сети, не обещая этого автоматически для конкретного WireSock и прямого TCP.
- [QUIC migration, RFC 9000 §9](https://www.rfc-editor.org/rfc/rfc9000.html#section-9),
  [CONNECT-IP/MASQUE, RFC 9484](https://www.rfc-editor.org/rfc/rfc9484.html),
  [MPTCP, RFC 8684](https://www.rfc-editor.org/rfc/rfc8684.html): инструменты миграции
  и переноса трафика с требованиями к конечным сторонам. Наш вывод — использовать
  как основу изолированного relay-прототипа; они не сохраняют произвольную игру
  при любой смене транспорта/сервера сами по себе.
- [.NET QUIC overview](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/quic/quic-overview):
  поддерживаемая Windows-платформа System.Net.Quic начинается с Windows 11 /
  Server 2022. Наш вывод — не ставить этот API обязательной зависимостью базовой
  функции Windows 10; проверить возможности уже используемого Go-движка.
- [The Update Framework](https://theupdateframework.github.io/specification/latest/):
  доверенные роли/ключи и метаданные защищают доставку от ряда подмен, откатов и
  устаревания. Наш вывод — оценить готовую реализацию для клиента и стратегий,
  не называть обычный SHA-файл полноценной независимой аутентификацией. Зеркало
  не должно получать собственное право подписывать код; отказ обновлений не
  останавливает уже работающее подключение.

## Что остаётся неизвестным до прототипа

1. Какая дополнительная DPI-стратегия поможет на реальных сетях пользователей
   и будет ли её выигрыш выше затрат/конфликтов. Исследование не заменяет пилот.
2. Можно ли обеспечить требуемую app-scoped VPN-границу с текущим прозрачным
   WireSock без смены архитектуры. Loopback-стенд даёт только часть доказательств.
3. Поддерживает ли наша точная версия WireSock/AWG мягкий handover с сохранением
   потоков при реальной смене физической сети. Протокол WireGuard — основание
   исследовать, а не ответ за конкретный драйвер/сервер.
4. Какой TCP/TLS-резерв лучше на наших Windows/сервере. Факт наличия протокола
   в документации не доказывает его работу в закреплённом бинарнике.
5. Нужен ли собственный relay после предыдущих исправлений. Решение принимается
   по остаточным отказам, а не по сложности или новизне технологии.
6. Каковы допустимые бюджеты CPU/памяти/задержки на слабой машине. Утвердить после
   одинаковых базовых и нагрузочных измерений; не выдавать короткий тест за
   подтверждение отсутствия утечки на длительной сессии.
